# RED Virt Log Viewer

Плагин для Sublime Text, предназначенный для локального анализа офлайн-сборов логов РЕД Виртуализации. Проект ориентирован на инженеров поддержки L2/L3, работающих с результатами `rvsupport` и другими выгрузками журналов Engine и хостов.

> **Статус: MVP 0.1 (этап 5).** Плагин можно ставить: папка задачи → индекс → Find Object → Show Timeline / Events Around. Journal UTC только при заданных `journal_year` и `journal_utc_offset`. QEMU май и VDSM август — не один инцидент. Хосты и объекты Engine — после MVP.

## Для чего нужен проект

При разборе обращения приходится находить нужные файлы, читать сжатые ротации, искать имя ВМ и её UUID, сравнивать записи Engine, VDSM и QEMU. RED Virt Log Viewer должен объединить эти действия в интерфейсе редактора.

Основной сценарий: **открыть сбор → найти объект → выбрать время → посмотреть связанные записи → перейти к исходным строкам**.

Инструмент предназначен для навигации и сопоставления фактов. Автоматическое определение причины инцидента не входит в MVP.

## Что работает в MVP 0.1

- Всё из этапов 1–3. Сессия из папок окна; SQLite — `~/.cache/red-virt-log-viewer/roots/<ключ-пути>/index.sqlite`.
- **Find Object**: кандидаты ВМ по каноническому UUID и именам из одного блока запуска QEMU.
- **Show Timeline**: хронология выбранной ВМ в интервале `[начало, конец)`; записи без `timestamp_utc_us` не входят (счётчик в шапке).
- **Events Around**: ±1 / ±5 / ±15 минут от времени строки под курсором, если оно есть в индексе. «Сейчас» с компьютера не подставляется.
- Journal: оба `journal_year` и `journal_utc_offset` → UTC; смена настроек помечает journal stale (Rebuild Index). Год не берётся с часов хоста.

Кеш: `~/.cache/red-virt-log-viewer/roots/<ключ от realpath корней>/index.sqlite` (не внутри сбора, не Postgres). Исходные логи не изменяются.

## Сценарий работы (MVP)

1. Открыть распакованный каталог **одного** обращения (`File → Open Folder`), не весь каталог тикетов.
2. Дождаться индекса (вкладка Session). Повторное открытие того же пути переиспользует SQLite.
3. Найти ВМ по UUID или имени из блока запуска QEMU (Find Object). Одноимённые ВМ с разными UUID выбираются отдельно. Хосты в MVP нет.
4. Show Timeline: интервал `[начало, конец)` по UTC для выбранной ВМ, либо пусто — страница timed-событий. Фильтров узла и уровня нет.
5. Открыть исходную запись (Enter на строке результата), включая фрагмент gzip/xz.
6. Events Around: ±1 / ±5 / ±15 минут от времени строки в индексе, не от часов компьютера.

Запись может не содержать UUID затронутой ВМ. Around смотрит все компоненты в окне, Timeline объекта — только связанные с выбранной ВМ.

## Объём MVP 0.1

Сборы, индекс, Find Object, Timeline выбранной ВМ и Events Around. Фильтры узла/уровня и объекты Engine как сущности — нет. Квота размера кеша не задана.

| Направление | Возможности | Сейчас |
| --- | --- | --- |
| Сборы | Распакованные каталоги; несколько источников в одной сессии | да |
| Чтение | Обычные текстовые файлы, `.gz` и `.xz` | да |
| Основные парсеры | Engine, VDSM, QEMU, текстовые выгрузки journal | да |
| Объекты | ВМ: UUID, наблюдения имён из QEMU launch, связь с VDSM `vmId` | да (хосты — нет) |
| Поиск | По объекту или буквальному тексту | Find Object и Search Text |
| Хронология | Окно `[start, end)` по UTC, Events Around ±1/5/15 мин; без фильтра узла/уровня | да |
| Источники | Переход к файлу и строкам; просмотр фрагментов сжатых файлов | да |
| Индекс | Локальный SQLite-индекс метаданных и связей; повторное использование и обновление | записи и identifiers |
| Управление | Прогресс, отмена операций, переиндексация, очистка кеша | да |

Произвольные текстовые файлы предполагается оставлять доступными для поиска даже при отсутствии специализированного парсера. Нераспознанный формат не означает отсутствие событий.

## Входные данные

Проект должен учитывать разные структуры сборов, например:

- `<сбор>/rv_info/logs/`;
- `<сбор>/log/`;
- `<сбор>/var/log/`;
- `<сбор>/rv_info/journalctl/`.

Компонент на этапе 1 определяется по пути. В следующих этапах формат будет подтверждаться по содержимому. Один сбор может содержать несколько компонентов независимо от варианта размещения Engine. Сбор, узел и компонент учитываются отдельно.

Пустые, повреждённые и неподдерживаемые файлы должны отображаться с соответствующим статусом. Наличие файла нулевого размера не считается успешной обработкой журнала.

Внешние и вложенные архивы `.tar.gz`, `.zip` и аналогичные контейнеры необходимо заранее распаковывать. Это ограничение не относится к чтению отдельных сжатых логов `.gz` и `.xz`.

## Принципы достоверности

- **Имя не является уникальным идентификатором.** Одноимённые ВМ с разными UUID не объединяются автоматически.
- **Связь должна иметь доказательство.** Для соответствия имени и UUID сохраняются файл, строки и время наблюдения, если оно известно.
- **Исторические имена учитываются отдельно.** Имя из старого лога не объявляется текущим без дополнительных оснований.
- **Время не угадывается молча.** Явный часовой пояс учитывается; отсутствующий пояс или год требует подтверждённого правила либо настройки источника.
- **Исходные записи сохраняют значение.** Результат должен вести к оригинальному тексту, включая стек исключения или блок запуска QEMU.
- **Неполнота видна пользователю.** Лимиты выдачи, отменённая обработка и пропущенные источники явно обозначаются.

Хронология отражает время, записанное узлами. Она сама по себе не устраняет рассинхронизацию их часов.

## Основа разработки

В качестве источника отдельных решений выбран [ovirt-log-analyzer](https://github.com/mz-pdm/ovirt-log-analyzer), проверенный на коммите [`ad6179a6622e49bc4f1682c16486555c04f29edb`](https://github.com/mz-pdm/ovirt-log-analyzer/tree/ad6179a6622e49bc4f1682c16486555c04f29edb) от 03.04.2018.

Планируется переиспользовать подходящие шаблоны Engine/VDSM и проверенные правила распознавания объектов и операций. RED Virt Log Viewer разрабатывается как самостоятельный плагин; полный CLI и архитектура кеша старого анализатора не переносятся.

Upstream распространяется под Apache-2.0. При переносе кода необходимо сохранить применимые уведомления, авторство и отметить изменения. Конкретные заимствования будут перечислены в `THIRD_PARTY_NOTICES.md`. Лицензия собственного кода проекта пока не определена.

## Установка и совместимость

Требования:

- Sublime Text 4, сборка **4050** или новее (проверено на **4200**).
- Плагин использует **Python 3.8** (`plugin_host-3.8`, файл `.python-version`).
- Стандартная библиотека: `gzip`, `sqlite3`, `lzma`. Если `lzma` недоступен, файлы `.xz` получают статус ошибки чтения, плагин не падает.

Установка для разработки — симлинк с именем без дефисов, чтобы относительные импорты Python работали:

```bash
ln -sfn /path/to/red-virt-log-viewer ~/.config/sublime-text/Packages/RedVirtLogViewer
```

Перезапустите Sublime Text. Основной вход: **File → Open Folder** на каталог задачи. Запасной: Command Palette `RED Virt: Open Support Folder`. `"native_folder_dialog": true` — системный диалог. Опционально `"tickets_root"`.

Лимиты по умолчанию: `page_size` 200, `max_line_bytes` 1 MiB, `direct_open_max_bytes` 32 MiB. Поиск читает файлы потоком. Квота кеша не задана.

Zip для передачи коллеге — в `USER_GUIDE.md` (без `.git` и без `tickets/`).

Запуск проверок ядра вне редактора:

```bash
python3.8 -m unittest discover -s tests -v
```

Подробный сценарий — в `USER_GUIDE.md`.

Подключение к Engine API, базе данных и production-узлам не планируется. Обработка выполняется локально, исходные файлы не изменяются, кеш хранится отдельно от сборов.

## Этапы реализации

1. Чтение каталогов и текстовый поиск с переходом к источнику. **Сделано.**
2. Парсеры, индекс и отображение состояния обработки. **Сделано.**
3. Связь имени и UUID из QEMU, поиск соответствующих записей VDSM. **Сделано (Find Object).**
4. Временные окна выбранной ВМ и Events Around; год journal из настроек. **Сделано.** Объекты Engine и фильтры узла — позже.
5. Проверки на образцах, ручная установка в Sublime и состав пакета. **Сделано (MVP 0.1).**

Произвольный текстовый поиск читает выбранные файлы потоком. Повторное чтение сжатого источника занимает время; мгновенный доступ к любой строке gzip/xz не гарантируется.

## Что не входит в MVP

- Автоматические диагнозы и экспертные сценарии.
- Наблюдение за живыми логами и удалённый сбор.
- Автоматическая распаковка архивов сборов.
- Интеграция с Engine DB и веб-интерфейс.
- Полноценная модель дисков и доменов хранения; их идентификаторы остаются доступны текстовому поиску.

## Работа с образцами

Полные клиентские сборы не должны попадать в репозиторий. Для тестов используются небольшие обезличенные фрагменты с сохранением проверяемой структуры сообщений и согласованной заменой имён и идентификаторов.

Проверки на искусственных данных, реальных образцах и внутри Sublime учитываются отдельно (см. таблицу выше). Непроверенные возможности не следует обозначать как готовые.
