# RED Virt Log Viewer

Плагин для Sublime Text, предназначенный для локального анализа офлайн-сборов логов РЕД Виртуализации. Проект ориентирован на инженеров поддержки L2/L3, работающих с результатами `rvsupport` и другими выгрузками журналов Engine и хостов.

> **Статус: проектирование и подготовка MVP 0.1.** Проверены отдельные шаблоны и функции стороннего анализатора на образцах логов. Рабочий плагин пока не реализован. Возможности ниже — согласованный план разработки, а не описание готового релиза.

## Для чего нужен проект

При разборе обращения приходится находить нужные файлы, читать сжатые ротации, искать имя ВМ и её UUID, сравнивать записи Engine, VDSM и QEMU. RED Virt Log Viewer должен объединить эти действия в интерфейсе редактора.

Основной сценарий: **открыть сбор → найти объект → выбрать время → посмотреть связанные записи → перейти к исходным строкам**.

Инструмент предназначен для навигации и сопоставления фактов. Автоматическое определение причины инцидента не входит в MVP.

## Планируемый сценарий работы

1. Открыть распакованный каталог сборов Engine и хостов либо добавить несколько каталогов в одну сессию одного обращения.
2. Получить список обнаруженных источников и состояние их обработки.
3. Найти ВМ или хост по имени либо UUID. При неоднозначном имени выбрать конкретный объект.
4. Отфильтровать записи по времени, объекту, узлу, компоненту и уровню сообщения.
5. Открыть исходную запись из результата поиска, включая многострочный контекст.
6. При необходимости посмотреть события всех объектов вокруг выбранной записи: ±1, ±5 или ±15 минут.

Запись может не содержать UUID затронутой ВМ. Поэтому поиск по объекту дополняется просмотром общего временного окна.

## Объём MVP 0.1

Все пункты в таблице запланированы.

| Направление | Возможности |
| --- | --- |
| Сборы | Распакованные каталоги; несколько источников в одной сессии |
| Чтение | Обычные текстовые файлы, `.gz` и `.xz` |
| Основные парсеры | Engine, VDSM, QEMU, текстовые выгрузки journal |
| Объекты | ВМ и хосты: имена, UUID и подтверждённые связи между ними |
| Поиск | По объекту или буквальному тексту |
| Хронология | Сортировка по определённому времени, фильтры, просмотр соседнего временного окна |
| Источники | Переход к файлу и строкам; просмотр фрагментов сжатых файлов |
| Индекс | Локальный SQLite-индекс метаданных и связей; повторное использование и обновление |
| Управление | Прогресс, отмена операций, переиндексация, очистка кеша |

Произвольные текстовые файлы предполагается оставлять доступными для поиска даже при отсутствии специализированного парсера. Нераспознанный формат не означает отсутствие событий.

## Входные данные

Проект должен учитывать разные структуры сборов, например:

- `<сбор>/rv_info/logs/`;
- `<сбор>/log/`;
- `<сбор>/var/log/`;
- `<сбор>/rv_info/journalctl/`.

Компонент определяется для каждого файла по пути и содержимому. Один сбор может содержать несколько компонентов независимо от варианта размещения Engine. Сбор, узел и компонент учитываются отдельно.

Пустые, повреждённые и неподдерживаемые файлы должны отображаться с соответствующим статусом. Наличие файла нулевого размера не считается успешной обработкой журнала.

Внешние и вложенные архивы `.tar.gz`, `.zip` и аналогичные контейнеры необходимо заранее распаковывать. Это ограничение не относится к чтению отдельных сжатых логов `.gz` и `.xz`.

## Принципы достоверности

- **Имя не является уникальным идентификатором.** Одноимённые ВМ с разными UUID не объединяются автоматически.
- **Связь должна иметь доказательство.** Для соответствия имени и UUID сохраняются файл, строки и время наблюдения, если оно известно.
- **Исторические имена учитываются отдельно.** Имя из старого лога не объявляется текущим без дополнительных оснований.
- **Время не угадывается молча.** Явный часовой пояс учитывается; отсутствующий пояс или год требует подтверждённого правила либо настройки источника.
- **Исходные записи сохраняют значение.** Результат должен вести к оригинальному тексту, включая стек исключения или блок запуска QEMU.
- **Неполнота видна пользователю.** Лимиты выдачи, отменённая обработка и пропущенные источники явно обозначаются.

Хронология отражает время, записанное узлами. Она сама по себе не устраняет рассинхронизацию их часов.

## Основа разработки

В качестве источника отдельных решений выбран [ovirt-log-analyzer](https://github.com/mz-pdm/ovirt-log-analyzer), проверенный на коммите [`ad6179a6622e49bc4f1682c16486555c04f29edb`](https://github.com/mz-pdm/ovirt-log-analyzer/tree/ad6179a6622e49bc4f1682c16486555c04f29edb) от 03.04.2018.

Планируется переиспользовать подходящие шаблоны Engine/VDSM и проверенные правила распознавания объектов и операций. RED Virt Log Viewer разрабатывается как самостоятельный плагин; полный CLI и архитектура кеша старого анализатора не переносятся.

Upstream распространяется под Apache-2.0. При переносе кода необходимо сохранить применимые уведомления, авторство и отметить изменения. Конкретные заимствования будут перечислены в `THIRD_PARTY_NOTICES.md`. Лицензия собственного кода проекта пока не определена.

## Что уже проверено

На подготовительном этапе выполнена проверка отдельных функций и шаблонов upstream-анализатора:

| Образец | Результат |
| --- | --- |
| Engine | Все 2 000 строк соответствовали шаблону; извлечены пять имён хостов |
| VDSM | Все 2 000 строк текущего образца соответствовали шаблону |
| Ротация VDSM `.xz` | Успешно распакована; все 64 247 строк соответствовали шаблону |
| QEMU | В блоке запуска найдена явная пара `-name guest=…` и `-uuid …` |
| Связь QEMU с VDSM | UUID из QEMU найден в поле `vmId` в 180 строках текущего VDSM и 5 684 строках ротации |
| Текстовый journal | Формат без года вида `Jul 12 13:26:46` требует отдельного парсера |

Эти результаты подтверждают пригодность образцов для разработки, но не гарантируют поддержку всех версий РЕД Виртуализации. QEMU и VDSM в проверенных образцах относятся к разным месяцам: связь по UUID подтверждена, единый инцидент по ним не восстанавливался. Проверка соответствия строк шаблону не равнозначна проверке полного цикла анализа.

## Организация проекта

| Путь | Ответственность |
| --- | --- |
| `RedVirtLogViewer.py` | Точка входа и регистрация команд Sublime |
| `ui/` | Команды, панели, вывод результатов и переходы |
| `core/` | Сессии, обнаружение файлов, чтение, индекс, объекты, поиск, хронология и фоновые задачи |
| `parsers/` | Разбор конкретных форматов журналов |
| `tests/` | Проверки ядра и парсеров |
| `tests/fixtures/` | Минимальные обезличенные примеры |
| `*.sublime-*` | Настройки, меню, команды и подсветка |

Ядро и парсеры должны работать без импорта `sublime`, чтобы их можно было проверять отдельно от редактора.

Подробное устройство индекса, контрактов парсеров и обработки времени будет описано в `ARCHITECTURE.md`.

## Установка и совместимость

Устанавливаемый пакет пока не подготовлен. Созданный каркас с пустыми ресурсами не является рабочим плагином.

Целевой редактор — Sublime Text 4. Минимальная сборка редактора, окружение Python, зависимости и поддерживаемые ОС будут зафиксированы после проверки реализации. Инструкция установки и использования появится в `USER_GUIDE.md` вместе с первым рабочим пакетом.

Подключение к Engine API, базе данных и production-узлам не планируется. Обработка должна выполняться локально, с сохранением исходных файлов и размещением кеша отдельно от сборов.

## Этапы реализации

1. Чтение каталогов и текстовый поиск с переходом к источнику.
2. Парсеры, индекс и отображение состояния обработки.
3. Связь имени и UUID из QEMU, поиск соответствующих записей VDSM.
4. Объекты Engine, временные фильтры и общая хронология.
5. Проверки на образцах, ручная проверка в Sublime и подготовка пакета.

Для больших файлов планируются потоковое чтение, порционная выдача и отмена задач. Произвольный текстовый поиск может требовать чтения выбранных файлов целиком. Повторное чтение сжатого источника также может занимать время; мгновенный доступ к любой строке gzip/xz не гарантируется.

## Что не входит в MVP

- Автоматические диагнозы и экспертные сценарии.
- Наблюдение за живыми логами и удалённый сбор.
- Автоматическая распаковка архивов сборов.
- Интеграция с Engine DB и веб-интерфейс.
- Полноценная модель дисков и доменов хранения; их идентификаторы остаются доступны текстовому поиску.

## Работа с образцами

Полные клиентские сборы не должны попадать в репозиторий. Для тестов используются небольшие обезличенные фрагменты с сохранением проверяемой структуры сообщений и согласованной заменой имён и идентификаторов.

Проверки на искусственных данных, реальных образцах и внутри Sublime необходимо учитывать отдельно. Непроверенные возможности не следует обозначать как готовые.
